# HCP v2 in the suite

The suite checks two versions of the Human Context Protocol: v1, frozen at
`1.0-draft-4`, and v2, at its latest draft, `2.0-draft-3` (November 2026,
[loyalagents/hcp-spec](https://github.com/loyalagents/hcp-spec), reviewed at
commit `b790561`). This page says how v2 fits into the suite, what the v2
checks cover and what they leave out, and what the review of Draft 3 turned up
for its editors.

## How a run picks its version

A run targets one version. `spec_version` names it (`1.0` or `2.0`) on the CLI
(`--spec-version`), in an API run's body and on the connect page. Left out on
the CLI and the API, the version is read from the `hcp_version` in the target's
discovery document, falling back to v1 when there is none to read. The connect
page always sends one, because the run page lists a version's groups before any
request is made.

Each version has its own catalogue (`HcpConformance.Catalog.all/1`), its own
checks (`lib/hcp_conformance/checks/` for v1, `lib/hcp_conformance/v2/checks/`
for v2) and its own reference implementation. The runner, the transcript, the
report, redaction, the private-network guard and the conformance hook's three
calls are shared. v1's checks, ids and report are unchanged.

## What changed from v1, as the suite sees it

| v1 | v2 | Consequence for the checks |
| --- | --- | --- |
| `conformance_level`, `authorization_profile`, `supported_transports` | `conformsTo` identifiers and `bindings` (§18, §19) | Discovery checks judge claims and their consistency instead of one level |
| The person and agents | A Management Client and Context Clients, on a governance plane and a context plane (§1.6) | One check per governance operation that a Context Client is refused |
| `/v1/preferences`, search, `PUT` | `/v2/entries`, query, revisions with `expectedVersion` (§9.2) | New paths, a version-conflict error, `HCP-Version` as a response header |
| An entry returned with two provenance fields redacted | A disclosure under a grant-scoped `ref`, with `standing` and `useUntil` (§7.4, §7.6) | Checks on what is withheld, on `ref` opacity and scoping, on the use-until ceiling |
| Scopes and restrictions | `access` details with approved purposes; scopes derived (§6.1.5) | Purpose is enforced, not only recorded |
| `userVerified`; accepting an inference rewrites its type | Confirmation records; assurance set by the provider (§3.5 to §3.8) | Checks that provenance is never taken from a request |
| `actorId`, `actorType`, free-text `detail` | `participants` and structured `data` (§3.9, §8.2) | Events are checked by member, not by matching text |
| — | Standing rules and directives (§6.3, §6.4) | A group of their own |
| Conflict detection in Core | In the Memory Manager Profile (§15) | Not checked yet; see below |

## What the v2 checks cover

127 checks in eleven groups, listed in [CHECKS-v2.md](CHECKS-v2.md). They cover
the First-Party package over the HTTP Binding: Core, the General Context
Profile, and the First-Party Authorization Profile through the hook.

| Group | Covers |
| --- | --- |
| `discovery` | Required members, vocabularies, claims against bindings, profile consistency and the members tied to a profile, described categories, the durability window (§18, §19) |
| `transport` | `HCP-Version` negotiation, bearer authentication (§9.3, §9.7) |
| `entries` | Create, get, revise, withdraw, hard delete; provider-set provenance; assurance; declaration-type rules; unknown members preserved; disclosures, `ref` and `useUntil` (§4.2, §5.2, §7.4, §7.6) |
| `idempotency` | Replays and key conflicts on create, revise and delete (§9.6) |
| `query` | Result shape, purpose and category bounds, default and ceiling, no padding, lexical order, no counts, no pagination, the audit event and what it must not hold (§5.2.1, §7) |
| `grants` | Grant objects, what each caller sees, temporary bounds, revocation, relinquishing, expiry, read-only grants, narrowed grants, unknown narrowing (§6.1, §6.2) |
| `governance` | Every governance operation refused to a Context Client; confirm, reject, recategorize and restrict purposes with `expectedVersion` (§3.8, §4.2.1, §4.2.6, §5.4, §6.1.9) |
| `rules` | Standing rules set, listed, audited, enforced on existing grants and at issuance; directives set, audited and delivered (§6.3, §6.4) |
| `audit` | Event structure, participants, cursor pagination and opacity, append-only (§3.9, §8, §9.5) |
| `export` | The export document, default contents, options, standing rules, the audit event (§5.4.1) |
| `responses` | Over every response of the run: the `HCP-Version` header, media types, RFC 9457 problems and their registered types, `Retry-After`, no 5xx (§9.3, §9.7, §9.8) |

Of the nine kinds of test §20.1 lists, the suite now has grant semantics,
minimization, audit completeness for the operations above, revocation
propagation at the provider, provenance, the governance plane, and the HTTP
Binding.

## What they do not cover yet

Each is a part of Draft 3 with no check behind it. A target can pass every v2
check and still fail these, so a pass is a claim about the surface above, not
about all of v2.

| Not covered | Section | What it needs |
| --- | --- | --- |
| JSON Schema validation of entries | §4.1.1, §20.1 | A JSON Schema validator in the suite. The entry rules are written out by hand, as v1's were. The published schemas were used once, by hand, to validate the reference implementation (below). |
| The MCP Binding | §10 | An MCP client: `server/discover` and the six tools. No v2 check is `mcp` only, so an MCP-only target gets `N/A` on the HTTP checks and nothing else. |
| The OAuth Interop Profile | §13 | A grant-flow harness: PAR, authorization details, token lifetimes. Only the discovery members are checked. |
| The VC Evidence, Health and Education profiles | §14, §16 | Issuing and verifying credentials, status lists. Only the discovery members are checked. |
| Conflicts and the Memory Manager Profile | §4.7, §15 | Relationships (`contradicts`), quarantine, resolution, proposals. Checked today: a target that accepts `model-inferred` entries claims the profile. |
| Relationships between entries | §4.2.3 | `supersedes`, `derivedFrom`, and what a Context Client may assert. |
| Import, and conversion from v1 | §4.3, §5.4.3 | Seeded v1 exports. |
| The disclosure summary | §8.6 | `GET /v2/disclosures`. |
| Onward sharing | §3.12, §5.2.8 | Grants electing it, `POST /v2/shares`. |
| Revocation notifications | §6.2.3, §9.9 | A notification endpoint the suite hosts, to receive Security Event Tokens. Until then every suite client has none, which is why `entries.use_until` holds targets to the one-hour ceiling. |
| Provenance on request | §7.4.1 | A grant with the `provenance` action. |
| Entry expiry | §4.2.4 | An entry whose `validUntil` passes during the run. |
| The Delegated Authorization Profile | §17 | Delegations, which only an Authorization Service establishes; the hook would need a call for it. |
| End-to-end encrypted storage | §4.8 | A trust-domain component. |
| Person-facing capabilities | §18.4, §18.5 | Not observable over a binding. |

The chat page ("Portable memory") still speaks v1 only. It sends a v2
connection to the run page.

## The v2 reference implementation

`HcpConformance.Reference.ServerV2`, served by a hosted suite at
`/reference/hcp-v2`, plays the part for v2 that the v1 reference plays for v1:
every v2 check passes against it in hook, static and anonymous mode
(`test/v2/reference_conformance_test.exs`), and each of its twenty deliberate
faults is caught by the check that guards the behaviour
(`test/v2/fault_detection_test.exs`).

It claims the First-Party package and nothing more, so it refuses
`model-inferred` entries and credentials as content. It implements what the
checks exercise; import, the disclosure summary, onward sharing, relationships
and notifications are missing from it as they are from the checks.

Its responses were validated once against the schemas published with Draft 3
(`schemas/2.0-draft-3`): the discovery document, an entry, a disclosure, the
create, query, get-entry, revise and withdraw results, a grant, a standing rule,
a directive, a problem, the export and nine event types. All validate but one:
the export with its audit log, for the reason in note 5 below.

## Review notes on Draft 3

Reading Draft 3 closely enough to write checks against it turned up places
where two implementers could reasonably build different things, or where the
text and the schemas differ. Each note says what the suite does in the
meantime. They are for the specification's editors, who ask for exactly this
feedback before Draft 4.

**The HTTP Binding**

1. **Media type of a success (§9.3).** The text says successful responses are
   `application/ld+json`; every HTTP example in §9.4 shows
   `Content-Type: application/json`. `responses.success_media_type` accepts
   either.
2. **The body of `GET /v2/grants` (§9.4.6).** The member that holds the grants
   is not named, where §9.4.13 to §9.4.15 name `delegations`, `rules` and
   `directives`. The schema for a client reading its own grant is the bare
   grant object, while the text says the call "returns grant objects". Where
   the directives of §5.2.6 go in that response is not said either. The suite
   reads a `grants` array or a bare grant.
3. **The body of `GET /v2/audit` (§9.4.7, §9.5).** Only `nextCursor` is named.
   The suite expects the events in `events`, as in v1.
4. **`reason` on withdraw (§5.2.5, §9.4.5).** Core requires a reason; the
   binding's `DELETE` shows no body and names no parameter. The suite sends
   `?reason=`, as v1 did, and does not check that it is recorded.
5. **`disclosed` for a Management Client's read (§8.2).** `context.read` lists
   "every entry disclosed", each with the `useUntil` it was given, and
   `audit-event.json` requires `useUntil`. A Management Client receives the
   entry, not a disclosure, and no `useUntil`. Either `disclosed` is for
   Context Clients only, or `useUntil` is optional. The reference lists the
   entry without `useUntil`, which the schema rejects; the suite checks
   `disclosed` only for a Context Client's read.
6. **Endpoints discovery does not publish (§9.2, §19.3).** `/v2/import` and
   `/v2/disclosures` have no member in the discovery document, though every
   other endpoint has one. A provider whose endpoints do not sit under one base
   cannot say where they are.
7. **Errors with no stated code.** Refusing a `model-inferred` write because the
   Memory Manager Profile is not claimed (§18.1), a credential as content
   without the VC Evidence Profile (§4.2.2), a standing rule naming neither
   operators nor `requires` (§6.3), and a grant a standing rule denies (§6.3)
   are all required, without saying which Core error applies. The suite accepts
   any 4xx for these.
8. **A revoked or expired grant (§6.2.2, §9.7).** "No request succeeds", but
   whether it fails as unauthenticated (401) or not authorized (403) is not
   said; the unauthenticated row covers "expired authorization evidence" only.
   The suite accepts both.
9. **Unknown resources for a Management Client (§5.2.2, §9.7).** Not authorized
   hides whether an entry exists from a caller who may not know. A Management
   Client may know, and for it, and for an unknown `ruleId` or route, no status
   is given. The suite accepts any 4xx.

**Core**

10. **`authorizedUnder` for a Management Client's write (§4.2).** The field is
    required and is "the grant under which this version was written". §6.1 says
    every HCP Client holds a grant, but no grant object is described for a
    Management Client, and whether it appears in `GET /v2/grants` is not said.
    The suite requires a string.
11. **Scope strings and `provenance` (§6.1.1, §6.1.5).** Scopes are
    `hcp:{category}:{action}` and derived from `access`, whose actions include
    `provenance`. Whether `hcp:{category}:provenance` is a scope is not said.
    The suite derives scopes for `read` and `write` only, and requires only
    that `scopes` grant nothing `access` does not.
12. **Older versions for a Context Client (§5.2.2).** `version` is a request
    field for every caller. Whether a Context Client may read a superseded
    version of an entry it can read now, and with which `useUntil`, is not
    said. Not checked.
13. **"The query text is not recorded" (§8.2)** is stated as a fact, without a
    requirement keyword. `query.text_not_logged` holds targets to it as a MUST,
    because the sentence gives the reason: the text can be as sensitive as the
    content.

**Conformance testing**

14. **The test hook (§20.2)** is left to "the suite specification". This suite
    defines it in [HOOK.md](HOOK.md). For v2 it had to add the Client Operator
    and the `access` details with purposes to the grant request. Draft 4 could
    cite it, or say what a hook must offer.
15. **Registering a notification endpoint (§6.2.3, §7.6).** The ceiling on
    `useUntil` depends on whether the client "has registered a notification
    endpoint", as do a client's legal-retention declaration and its claims,
    "declared at registration". How a client registers any of them is not
    defined, under either authorization profile: no metadata member is named.
    A hook-issued client has none, so the suite can test the one-hour ceiling
    but not the 24-hour and 30-day ones.
16. **Claiming a binding whole (§18.1)** makes import, the disclosure summary
    and onward sharing part of every HTTP Binding claim. A pilot that has not
    built them cannot list the binding, and so cannot list anything that needs
    it. Draft 4 could say whether that is intended for pilots.

## Following the next draft

When Draft 4 lands: update `HcpConformance.Spec`, read its changelog entry
(each draft lists its changes to the wire), change the checks and the reference
together, and regenerate [CHECKS-v2.md](CHECKS-v2.md). A check for something a
draft removes is deleted, not skipped. If two v2 drafts ever need checking side
by side, a draft becomes a third catalogue, as v2 became a second.
